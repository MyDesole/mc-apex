## Приложение Б. Остальные домены

Небольшие области, которые не попали в крупные главы.

### Б.1. Search — глобальный поиск

Два файла: `SearchController` и `GlobalSearchService`.

```
GET /api/search
```

Поиск идёт по нескольким сущностям сразу (игроки, кланы, темы форума) и возвращает сгруппированный результат — фронтенд показывает его выпадающим списком в шапке.

Отдельно от глобального поиска существуют **частные поиски внутри разделов**, и это разные эндпоинты с разной логикой:

| Эндпоинт | Где |
|---|---|
| `GET /api/forum/search` | поиск по темам форума |
| `GET /api/chat/search` | поиск по диалогам |
| `GET /api/chat/conversations/{id}/search` | поиск по сообщениям конкретного диалога |
| `GET /api/admin/players/search` | поиск игрока в админке (для жалоб) |

Разделение осмысленно: у каждого поиска свои права доступа и своя область видимости. Глобальный поиск не должен показывать приватные сообщения, а поиск в админке работает по игрокам, которых обычный поиск не отдаст.

### Б.2. Og — картинки для превью ссылок

Два файла: `OgController` и `OgImageRenderer`.

Когда ссылку на сайт кидают в Discord или Telegram, мессенджер запрашивает Open Graph-картинку. Домен генерирует её **на сервере**: рисует изображение с ником игрока, тиром и статистикой, чтобы превью выглядело как карточка, а не как серая заглушка.

Это же отвечает за `og:image` для профилей и кланов — поэтому ссылка на игрока в чате разворачивается в картинку с его тиром.

### Б.3. Project — «Что нового» и роадмап

| Файл | Назначение |
|---|---|
| `ProjectController` | публичное чтение |
| `AdminProjectController` | управление из админки |
| `Models/ChangelogEntry` | запись в «Что нового» |
| `Models/RoadmapItem` | пункт роадмапа |
| `Services/ProjectService` | логика |

Публично:

```
GET /api/project/changelog
GET /api/project/changelog/{slug}
GET /api/project/roadmap
```

Админка (полный CRUD):

```
GET|POST        /api/admin/project/changelog
PUT|DELETE      /api/admin/project/changelog/{entry}
GET|POST        /api/admin/project/roadmap
PUT|DELETE      /api/admin/project/roadmap/{item}
```

Отдельный `slug` у записи changelog нужен для прямых ссылок: `/changelog/название-записи` на фронтенде.

### Б.4. Users — пользователь и роли

Самый «низкоуровневый» домен: здесь живёт модель `User` и всё, что касается аккаунта целиком.

| Файл | Назначение |
|---|---|
| `Models/User.php` | модель пользователя |
| `Concerns/HasRoles.php` | трейт проверки ролей |
| `Controllers/Api/Admin/UserController.php` | управление пользователями из админки |
| `Controllers/Api/Admin/RoleController.php` | выдача ролей |
| `Requests/Admin/BanUserRequest.php` | валидация бана |
| `Requests/Admin/UpdateRoleRequest.php` | валидация смены роли |
| `Requests/Admin/VerifyUserRequest.php` | ручное подтверждение почты |
| `Notifications/FriendRequest.php` | уведомление о заявке в друзья |

**Трейт `HasRoles`** — то, чем пользуются middleware и политики. Он отвечает на вопросы вида «есть ли у пользователя одна из этих ролей», и именно он позволяет маршрутам писать `role:moderator,admin`.

Админские возможности по пользователю: сменить роль, забанить с причиной и сроком, снять бан, вручную подтвердить почту, отвязать Minecraft-ник.

### Б.6. Server — панель игрового сервера

Домен управляет игровым сервером **apevpvp.pro** (`168.113.181.145`,
каталог `/opt/minecraft/server`, WindSpigot 2.1.4 на Java 17) прямо из
админки сайта.

**Доступ.** Роль `server_admin` («Администратор сервера») и `admin`. Роль
живёт в `HasRoles::SERVER_ROLES`; она также входит в `STAFF_ROLES` и
`UNRANKED_ROLES` (не участвует в рейтингах). Модератор панель **не
видит**: раньше проверка была «модератор или админ», теперь — отдельный
список ролей.

**Как устроено.** Сайт не запускает процессы Minecraft сам: на сервере
лежит скрипт `/opt/minecraft/server/apex-panel.sh` с подкомандами
`status | players | plugins | console N | start | stop | restart | cmd |
get-start | set-start | files | read | write | archives | apply-zip |
rm-archive | backups | restore`. `GameServerService` ходит туда по SSH и
разбирает ответ. Плюс этого:

- сайту не нужно знать, как именно устроен запуск (screen, systemd — неважно);
- команда запуска читается и пишется как `start.sh` на сервере;
- при смене способа запуска правится один скрипт, а не PHP.

**Доступ по ключу.** На проде создан ключ
`backend/storage/app/server/id_ed25519` (владелец `www-data`), его
публичная часть добавлена в `/root/.ssh/authorized_keys` игрового сервера.
Пароль в коде не хранится. Адрес, пользователь и каталог — в
`config/services.php` → `game_server`, а не через `env()` в сервисе:
после `config:cache` на проде `env()` вне конфигов возвращает `null`.

**Эндпоинты** (`role:server_admin,admin`, префикс `/api/admin/server`):

| Метод | Адрес | Что делает |
|---|---|---|
| GET | `/status` | состояние, pid, аптайм, память, диск, нагрузка, игроки, размер каталога |
| GET | `/console?lines=150` | хвост `logs/latest.log` |
| GET | `/players` | точное число игроков через `list` |
| GET | `/plugins` | jar-файлы в `plugins/` |
| POST | `/start` \| `/stop` \| `/restart` | питание сервера |
| POST | `/command` | команда в консоль (say, list, whitelist…) |
| GET | `/start-command` | текущий `start.sh` |
| PUT | `/start-command` | сохранить `start.sh` (в содержимом обязательна `java`) |
| POST | `/upload` | загрузка файла в корень или `plugins` |
| GET | `/files` | список редактируемых конфигов |
| GET | `/file?path=` | содержимое конфига |
| PUT | `/file` | сохранить конфиг |
| GET | `/archives` | архивы в очереди и бэкапы |
| POST | `/archives` | залить zip в очередь |
| POST | `/archives/{name}/apply` | применить архив |
| DELETE | `/archives/{name}` | удалить архив |
| POST | `/backups/{name}/restore` | откатить к бэкапу |

**Редактор конфигов.** Панель отдаёт список редактируемых файлов: всё в
корне сервера (`*.properties`, `*.yml`, `*.yaml`) и конфиги плагинов
(`plugins/<Плагин>/*.yml|json|properties`, глубина 2). Читается и
пишется только то, что проходит проверку: путь без `..`, без ведущего
`/`, только из `[A-Za-z0-9_./-]`, расширение из
`properties|yml|yaml|json|txt|conf`, размер до 500 КБ. Проверка двойная —
в PHP (`assertConfigPath`) и в скрипте (`check_path`).

**Архивы сервера.** Загрузка идёт на сайт (лимит 200 МБ), затем `scp` в
`/opt/minecraft/updates/`. Применение выполняет скрипт:

1. остановить сервер (штатный `stop`, ждём до 90 с);
2. `tar czf /opt/minecraft/backups/server-<дата>.tar.gz -C /opt/minecraft/server .`;
3. распаковать архив поверх каталога — на сервере нет `unzip`, поэтому
   используется `python3 -m zipfile -e`;
4. запустить сервер заново.

Файлы, которых нет в архиве, не удаляются — только перезаписываются. На
тестовом прогоне (архив с одним файлом) цикл занял 3 секунды, бэкап
каталога 110 МБ — 72 МБ.

**Лимиты загрузки.** На проде подняты до 200 МБ:
`/etc/php/8.4/fpm/conf.d/99-apex-panel.ini` (`upload_max_filesize = 200M`,
`post_max_size = 210M`, `max_input_time`, `max_execution_time` = 600) и
`client_max_body_size 210m` в `/etc/nginx/sites-available/default`.
Проверено запросами: 60 МБ доходит до приложения, 220 МБ отдаёт 413 от
nginx.

**Ограничения загрузки файлов.** Расширения: `jar, zip, yml, yaml, json,
txt, properties, conf, sh`; папки — корень сервера и `plugins`. Каталога
`config` на этом сервере нет (Spigot, не Paper).

**Безопасность.** Процессы запускаются массивом аргументов (`proc_open`
без оболочки), поэтому текст команды из консоли не может стать аргументом
`sh`. Команда в консоль ограничена 300 символами и уходит в screen только
как строка ввода.

**Интерфейс.** Раздел «Сервер → Игровой сервер» в админке: карточки
состояния, консоль с автообновлением, поле команды, загрузка обновлений,
плагины, редактор конфигов, архивы с бэкапами и редактор `start.sh`. У
`server_admin` админка показывает только этот раздел: фильтр разделов в
`AdminView` учитывает роли пункта меню.

### Б.5. Core — главная и настройки сайта

Самый маленький домен (4 файла), но именно он собирает данные для главной страницы и отдаёт настройки сайта наружу.

Через него на фронтенд попадают:

- объявление сайта (`site_settings`), которое показывается на всех страницах;
- данные для главной: топ игроков, статистика проекта;
- публичные флаги функций — чтобы интерфейс знал, что скрыть.

**Связка с Control.** Флаги функций хранятся в `site_settings`, меняются через домен `Control`, а применяются в двух местах: на бэкенде — middleware `EnsureFeatureEnabled`, на фронтенде — скрытием разделов. Если функцию выключили, а интерфейс о ней не знает, пользователь получит ошибку вместо аккуратного скрытия — поэтому флаги и отдаются через `Core`.
