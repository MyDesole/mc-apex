# Minecraft: сборка, деплой и откат

GitHub → Actions → **Minecraft** → **Run workflow**.
Workflow запускается из `main`; `source_ref` выбирает ветку/тег/коммит с исходниками.
Сейчас исходники находятся в `design/minecraft-style`, а не в `main`.
Незакоммиченные локальные изменения в сборку не попадают: сначала commit и push.

## Команды в форме запуска

| action | Что произойдёт |
| --- | --- |
| `build` | Собрать выбранные плагины, сохранить JAR в Artifacts и загрузить релиз на сервер. Сервер продолжает работать без изменений. |
| `status` | Показать состояние сервера и список загруженных SHA релизов. |
| `deploy` | Собрать, остановить сервер штатной командой `stop`, сохранить полный архив сервера, заменить только выбранные JAR и запустить сервер. Игроки отключатся. |
| `rollback` | В `rollback_sha` указать полный SHA выкладки из Summary: вернуть прежние JAR, перезапустить. Миры и текущие данные плагинов сохраняются. |

Поле `plugins`: `all`, `clanwars`, `tiertests`, `auth`, `skins`.
`all` собирает плагины, исходники которых доступны в выбранной ветке.
Сейчас в GitHub есть ClanWars и TierTests. Auth и Skins лежат только локально
и исключены через `.gitignore`: `all` пропускает их с предупреждением,
а явный выбор `auth`/`skins` завершится понятной ошибкой, пока исходники не будут
закоммичены и отправлены в выбранную ветку. Исключённые файлы автоматически
не публикуются.
`source_ref` по умолчанию — `feature/fastbridge-perks`. Для воспроизводимой выкладки
лучше указать точный SHA проверенного коммита. Форма Run workflow требует запуска
именно workflow из `main`, даже если исходники выбраны из другой ветки.

Команда из WSL:

```bash
gh workflow run minecraft.yml --ref main -f action=build -f source_ref=design/minecraft-style -f plugins=all
gh run list --workflow minecraft.yml --limit 5
```

Для выкладки замените `action=build` на `action=deploy`.
Сборки одного ещё не выложенного SHA можно повторять. После выкладки содержимое
релиза неизменно; для следующей выкладки нужен новый исходный коммит.
Разные наборы плагинов одного SHA до выкладки заменяют подготовленный релиз.

## Что меняется на сервере

| Исходники | Установленный JAR |
| --- | --- |
| `minecraft-plugin` | `plugins/ApexAuth.jar` |
| `minecraft-skin-plugin` | `plugins/ApexSkins.jar` |
| `minecraft-clanwar-plugin` | `plugins/ApexClanWars.jar` |
| `minecraft-tiertest-plugin` | `plugins/ApexTierTests-Tactics.jar` |

Конфиги, миры, ядро и сторонние плагины не заменяются. Плагины других версий
Minecraft из репозитория не выкладываются на работающий WindSpigot 1.8.8.
Зависимости берутся с действующего сервера и не публикуются как артефакты.
Артефакты сборки хранятся в GitHub 30 дней.

На сервере:

- `/opt/minecraft/ci/releases/<SHA>/` — подготовленные JAR;
- `/opt/minecraft/ci/backups/<SHA>/` — прежние JAR и `server.tar.gz`;
- `/usr/local/sbin/apex-ci` — root-owned обработчик ограниченных команд;
- `/usr/local/bin/apex-ci-gateway` — SSH gateway пользователя `minecraft-ci`.

Архив `server.tar.gz` содержит миры, конфиги и данные плагинов на момент
выкладки, после штатной остановки. Автоматический rollback восстанавливает
только JAR, чтобы не терять прогресс игроков. Для восстановления мира или данных
из архива нужен администратор; автоматический откат не отменяет миграций данных.
Бэкапы не удаляются автоматически: следите за свободным местом на сервере.

При ошибке установки/запуска выполняется попытка вернуть прежние JAR и запустить
сервер. Проверка старта ждёт открытия TCP-порта 25565 до 240 секунд;
она не гарантирует корректную работу всех игровых механик. После выкладки
проверьте лог и зайдите в игру.

## Доступ

Environment `minecraft-production`: `MC_HOST`, `MC_KNOWN_HOSTS`, `MC_SSH_KEY`.
Ключ отдельный, с принудительной SSH-командой и запретом forwarding/PTY.
Пользователь не получает произвольную root-оболочку. Обработчик разрешает
только status, deps, stage, deploy и rollback, проверяет SHA и состав архива.
Операции сериализуются в GitHub и серверной блокировкой.

Проверка обработчика без живого сервера:

```bash
python3 -m unittest discover -s ops/minecraft -p 'test_*.py' -v
```

## FastBridge-патч

Ветка `feature/fastbridge-perks` содержит `build-fastbridge-patch.sh`.
Workflow автоматически собирает только классы FastBridge поверх установленного
ApexTierTests: остальные функции сохраняются. По умолчанию выбран `tiertests`.
Базовый JAR скачивается с сервера; его SHA256 записан внутри артефакта.
Если установленный JAR изменился между сборкой и выкладкой, деплой завершается
до остановки сервера: сначала пересоберите патч.
